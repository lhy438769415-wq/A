# 专项说明：夜间数据源同步易被 Baostock 黑名单封禁

> 写给：交易员（非程序员）。全文大白话，技术词第一次出现都带解释。
> 状态：现行有效（基于代码实测 + 版本记录核实，非凭记忆估算）
> 关联：`config/settings.py`、`core/data_provider.py`、`tools/fetcher_baostock.py`、`README.md` V9.16/V9.18/V9.19

---

## 0. 一句话结论

本系统用的是 **Baostock**（一个免费、免注册、谁都能连的 A 股行情数据源）。它**按 IP 地址限流**：同一个 IP 同时只能有 5 个连接，超了或请求太密就会被服务器暂时"拉黑"（封禁）。我们习惯**收盘后（18:00 之后）** 才同步数据，而这时恰好是所有人都在拉数据的晚高峰，所以"夜间同步容易被黑名单"是真实存在的现象。系统已经做了几层防护，但**被封时最正确的做法只有一个：停手，过几小时或第二天早晨再来，千万别反复重跑**（重跑反而会把封禁时间拉长）。

---

## 1. 先说清楚几个名词（避免黑话）

| 名词 | 大白话解释 |
|---|---|
| **Baostock** | 本项目唯一的数据源（"data source"，就是提供股票历史行情的服务）。特点：**免费、免注册、公开**，所以用它的人非常多。 |
| **黑名单 / 封禁** | Baostock 服务器觉得你这台机器"太吵"（连接太多或太频繁），就暂时拒绝你的请求，返回一个带"黑名单"字样的错误。不是账号被封（你也没账号），是**你的 IP 被临时限流**。 |
| **IP（网络地址）** | 你在互联网上的临时门牌号。如果你开 VPN、或用公司/家里路由器（NAT 网络地址转换，很多人共用一个出口 IP 的技术），**你这个 IP 是和别人共享的**——别人猛拉数据，也可能把你一起带进黑名单。 |
| **并发连接 / Worker（工作进程）** | 同步时是"多开几个窗口同时下载"来提速。开几个窗口 = 几个并发连接。 |
| **夜间同步** | 本系统只在**交易日 18:00 数据归档后**才做行情同步与分析（盘中拿不到当日完整数据，只能看昨天的 T-1 数据）。所以"同步"天然发生在收盘后的傍晚/夜间。 |

---

## 2. 为什么"夜间同步"特别容易中招（四大成因）

下面每一条都标了它在代码/文档里的出处，可查证。

### 成因 A：Baostock 是公开免费源，服务端按 IP 限流
Baostock 不收钱、不登记，所有人共用一套服务器。`config/settings.py:41` 的注释写明：

> Baostock 服务端对同一 IP 的并发 TCP 连接**硬限制为 5**。

超过 5 个并发连接，多出来的就会失败、进而触发限流/封禁。这是数据源本身的"出身"决定的——免费源为了不被挤爆，只能靠限流自保。

### 成因 B：我们自己机器的并发曾经超额（现已修）
早期同步开 **6 个 Worker（6 个并发窗口）**，但服务端只放 5 个。`config/settings.py:42-43` 注释记录了实测：

> 实证：6 Worker 时第 6 个连接即使重试 3 次也必定超时（2026-07 连续验证）。

现在 `MAX_WORKERS` 默认值已改成 **5**（`settings.py:44`），与硬上限对齐，实测"零报错、一次完成"。但如果你手动把环境变量 `MAX_WORKERS` 调到 6 以上，又会踩回这个坑。

### 成因 C：被封后"反复登录"会把封禁时间拉长（死亡螺旋）
这是最坑的一点。旧代码逻辑是：被封了 → 自动重试登录 → 又失败 → 再重试……`README.md`（V9.18 版本记录）明确记载：

> 修复此前"每次同步产生 **≥9 次失败登录**反复延长封禁"的死亡螺旋。

也就是说，被封是**临时的**（通常几小时就解封），但如果你不停重试，每次失败登录都在告诉服务器"我还在猛敲"，服务器就会把你的封禁**顺延得更久**。**所以"被封后还一直重跑"是最糟的操作。**

### 成因 D：共享 IP / VPN / 局域网，别人的流量也算你头上
如果你连着 VPN，或家里/公司网络是多人共用一个出口 IP，那么**同一时段别人也在用 Baostock**（或任何走这个 IP 的服务），累积的请求量会把"你的 IP"推过阈值，你跟着被封——即使你这台机器明明很克制。

### 附带说明：为什么偏偏"夜间"更明显
本系统要求 18:00 之后才同步（详见 `docs/archive/system_logic_audit.md:7`："所有分析必须在交易日 18:00 数据归档后进行"）。而收盘后是所有散户量化爱好者统一拉数据的**晚高峰**，服务端压力最大、限流最敏感。于是"你一下班想同步 → 正好撞上高峰 → 容易触发封禁"成了一个稳定的体感现象。

> 说明：成因 A/B/C 是**代码层面已证实**的硬事实；成因 D 与"夜间高峰"是**基于网络架构和作息的合理推断**（免费源 + 晚高峰 = 限流高发），属于高概率但非代码直接证明的补充说明，如实标注。

## 3. 系统已经做了哪些防护（代码层面，已落地）

不是只发现问题、啥也没做。以下几层防护都是真实写进代码的：

| 防护 | 做法 | 出处 |
|---|---|---|
| **被封立即终止，不重试** | 新增 `BsBlacklistedError` 异常，从 `fetcher_baostock.py` → 适配层 → `_fetch_worker` → 主循环**四层穿透**，一旦检测到"黑名单"字样**立刻停掉整批同步**，绝不重试。 | `tools/fetcher_baostock.py:24-26`、`core/data_provider.py:972-974`、`1042-1055`、`1308-1318` |
| **并发数对齐硬上限** | `MAX_WORKERS` 默认 5，不超额占用连接。 | `config/settings.py:41-44` |
| **扫描/推送阶段彻底不连 Baostock** | 股票中文名改为本地缓存 + `data/stock_names.json` 持久化（`get_stock_name()` 不再联网），扫描和推送环节**完全不碰数据源**，黑名单概率大幅下降。 | `README.md` V9.19 版本记录 |
| **登录/查询/登出超时保护** | `bs.login()` / `query_*()` / `bs.logout()` 都包了 `_run_with_timeout()`，避免底层 socket（网络套接字，即那条看不见的通信通道）在 VPN 不稳时无限卡死。 | `tools/fetcher_baostock.py`（`_run_with_timeout` 及多处调用）、`README.md` V9.16/V9.18 |
| **看门狗强杀卡死 Worker** | 某个下载任务"永远不返回"时，看门狗会在超时上限内**强制杀掉进程池**，不让一只慢票把整批同步拖垮。 | `core/data_provider.py:319-392`（`_drain_futures_with_watchdog`）、`tests/verify_p07_sync_watchdog.py` |
| **发现阶段后立即登出** | 增量发现（查新股/中文名）完成后马上登出主连接，避免后续漫长下载中连接空闲超时断开。 | `core/data_provider.py:977-984` |

## 4. 你（交易员）遇到黑名单时，照着做就行

这是最关键的"操作手册"部分，记住要点：**被封 = 停手等解封，别硬刚。**

1. **看到 `🚫 Baostock 黑名单封禁！终止本次同步` 这类提示**：
   - 说明本次同步被服务器拦了。**直接关掉、别再点"同步"**。
   - 已成功下载的部分**已经落库**（写进了 `baostock.db`），不会丢，也不会"白跑"。
2. **等多久再试**：通常等 **几小时** 或 **第二天早晨**（早高峰前）再跑一次即可。Baostock 的封禁一般是临时性的。
3. **一天同步一次就够**：
   - 日线：每天收盘后（≥18:00）跑 **1 次**。
   - 周线：**周五收盘后或周末**跑 **1 次**（周一~周四跑没新数据，纯属白费连接配额，见 `docs/周线接入操盘台_方案.md:314`）。
4. **不要反复点、不要为"没同步完"焦虑**：同步是**按天增量**的——已经拉过的交易日会自动跳过（`skipped`，见 `data_provider.py` 日志里的 "Skipped/NoNewData"），重跑只会补当天的差量，不必一气呵成。
5. **如果长期、频繁被封**：
   - 检查 `MAX_WORKERS` 是否被手动调高（应 ≤ 5）；
   - 检查是否开着 VPN（共享 IP 风险，见成因 D）；
   - 检查同网络有没有别的程序也在猛拉 Baostock/AkShare 类数据源。

## 5. 残留风险与待办（诚实清单）

| 项 | 现状 | 建议 |
|---|---|---|
| 数据源单一 | 目前**只**用 Baostock（免注册免费源），一旦被封只能干等，没有备选源兜底。 | 如未来要提升稳定性，可考虑接入备选源（如 Tushare，需 token）做降级，但会增加成本与维护。当前按"稳定优先"未做。 |
| 共享 IP 不可控 | VPN / 局域网 NAT 导致的连带封禁，本机无法规避。 | 如频繁中招，可尝试直连（关 VPN）或在网络空闲时段同步。 |
| 夜高峰并发不可控 | 晚高峰服务端压力大是外部因素，代码层面无解。 | 错峰：清晨或上午同步，避开 18:00–22:00 高峰。 |
| 自动防护已就位但需手册配合 | 代码已做到"被封立即停"，但**人为反复重跑**仍会延长封禁。 | 把本文第 4 节"操作手册"当成铁律：被封即停手。 |
