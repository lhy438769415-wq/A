# Web 操盘台 v2 — 原型设计「重新评估」（纠偏书 + TSP 借鉴重估）

> 依据 2026-09-08 全天对话重新锚定方向。本文**不修改**现有原型 HTML，而是把走偏的地基推倒重设，作为后续重建的准绳。
> **本轮新增（用户 15:34 补充）**：把 GitHub `tick-stock-panel`（TSP）的借鉴也纳入评估——当初的"借/不借"清单是按"只读查看器"假设打的，现在地基变了（操作进 Web、TV 宿主、Tk 退役），必须在新地基上重估一遍。

## 0. 一句话结论

之前把原型当成"**4→7 页的只读查看器**"来做，这是错的地基。正确的地基是：一个以**淘汰 Tk、跑通交易员 6 步闭环**为目标的**通用可插拔 PA 策略框架界面**。今天几轮对话已经把错路暴露清楚，接下来应**按新地基重建原型**，而不是在旧 HTML 上补丁式修改。

**关于 TSP 借鉴的关键修正**：当初"借 TSP 的页面分类（看板/自选/策略/回测/数据）"是**借错了部位**——TSP 是"监控/研究员工作台"，页面多为"查看"；而我们新地基要求"操作（同步/扫描）也进 Web"。所以应**少借 TSP 的页面分类、多借 TSP 的操作型 UX（SSE 流式进度、触发即看）和后端架构**，并只借它的视觉语言（纯样式，与框架无关）。

## 1. 今天踩偏的 4 个坑（为什么之前是错路）

1. **场景评审写成了"系统页面点击流"**（A 档 = 打开看板→点事件流），不是交易员真实操作。被你一眼识破："交易员每天的高频操作是这样的吗？"
2. **把"缺口"当成了普适高频项**（缺口存活列、按周存活检查当成所有交易员标配）。违背你强调的："本工具是灵活添加策略的通用框架，不是每个时期都关注缺口"。
3. **原型定位成"只读看+筛"**，导致同步/扫描不在 Web 里，我甚至让你"继续用 Tk 点下载行情"——直接撞第 8 条决策"Tk 最终退役、Web 是唯一长期界面"。
4. **一轮轮补丁式迭代**（UX 评审→改、场景评审→改、TV→改），每次只动局部，从没回头重校地基，越改越偏。

> 第 4 坑的根因之一：当初对 TSP 的借鉴是"静态借用页面皮"，没有随地基变化重新审视——本次重估补上这一刀。

## 2. 重新锚定的正确地基（今天已确认的事实）

- **工具定位**：通用、可插拔策略的 PA（价格行为）量化扫描框架。GUI 不得写死任何单一策略逻辑（尤其不能"缺口中心化"）；策略与信号一律从注册表动态读取 `get_metadata()['display_name']`，禁止硬编码中文花名。
- **交易员 6 步闭环**（你亲定的）：①同步数据 → ②扫描策略(初筛) → ③TV 里打开高质量形态(人工精筛) → ④制定交易计划 → ⑤持仓管理 → ⑥复盘分析(含回测)。
- **GUI 职责边界**（哪些归工具、哪些归人）：
  - ①同步、②扫描：**工具做**，且**必须进 Web**（这是淘汰 Tk 的前提）。
  - ③TV 精筛：**桥接/宿主**——Web 内嵌真 TV 控件 + 旁置 PA 证据（失效价/证据列/EV），不复制图表工作站。已验证可行，已做进信号抽屉。
  - ④计划：部分工具（`weekly_ambush_plan.md` 雏形 + 每信号计划记录）、部分人工。
  - ⑤持仓：基本人工（在券商/同花顺），GUI 只做跟踪/提醒，**不下单**。
  - ⑥复盘(含回测)：工具做（`journal` 表已存在 + 回测页）。
- **字段/命名铁律**：所有策略名、信号字段必须对齐真实注册表与 `signal_archive` 表结构，不出现无数据源字段。
- **红线 D5 修订**：Web 详情 K 线从"lightweight-charts 库"改为"内嵌 TV 控件"（待你拍板，但原型已按此落地）。

## 3. TSP 借鉴在新地基上的重估（本轮核心）

> 下列"借/不借"是在**新地基（操作进 Web + TV 宿主 + 通用可插拔 + Tk 退役）**下重评的。原"借/不借"清单（首轮 grill-me）是按"只读查看器"假设打的，有 3 处需要翻转。

### 3.1 应借（重评后有效或应升级）

| TSP 要素 | 重评结论 | 理由（新地基视角） |
|:---|:---|:---|
| **视觉语言**（近黑底 HSL + 1px 边框无阴影 + 数字等宽 + 细滚动条） | ✅ 借，纯样式 | 与框架无关，直接套；A 股红涨绿跌 TSP 本就如此，颜色一行不改 |
| **SSE 流式进度 + 触发即看**（TSP 用 SSE 持续推进度） | ✅ **升级为必借**（原清单未单列） | 新地基要求同步/扫描进 Web 带"进度条+终止"，正是 TSP 的强项；原只读假设下用不上，现在变成核心 |
| **后端架构**（FastAPI 多 router：data / strategy / backtest + SSE 端点） | ✅ **升级为必借**（原清单未单列） | 当初选 React 是"借皮"，现在 Web 必须跑真实同步/扫描，FastAPI 后端架构参考价值骤升；TSP 的 router 分层可直接参照 |
| **Data 页"数据画像"**（覆盖到哪天/缺哪些票/同步历史/质量体检） | ✅ 借 | 对应第①步同步，零风险，把状态栏小字升级成面板 |
| **自选多分组 + 表格/卡片双视图** | ✅ 借 | 对应第⑤步跟踪，比现关注列表强一档 |
| **策略卡片/Screener**（6 策略各一张卡） | ✅ 借**但动态化** | 对应"通用可插拔"——卡片必须循环注册表生成，禁硬编码花名 |
| **回测可视化**（净值曲线/回撤/胜率） | ✅ 借（第⑥步） | 本系统回测引擎已有数据，缺的正是这张皮 |

### 3.2 不应借（维持原结论，且新地基下更明确）

| TSP 要素 | 不借理由 |
|:---|:---|
| **实时监控 / 盘中弹窗 / 语音播报** | 本系统是 Baostock 离线 T+1，无实时行情，这些是空壳 |
| **连板梯队 / 概念轮动 / 异动偏离 / 行业轮动** | 打板/短线生态，与 Al Brooks 摆荡定位不符 |
| **市场环境 Regime（情绪周期 6 阶段）** | 撞你定的红线"市场状态判断交给人" |
| **因子挖掘 / 62+ 因子库 / RSI 等** | 撞 PA 铁律：成交量/指标/基本面不得入因子 |
| **TickFlow/同花顺数据源、DuckDB 存储** | 命根子（584MB SQLite，结构冻结），且换源要 Key、部分收费、有合规风险 |
| **页面大杂烩（24 页监控工作台）** | 见 3.3——这是**借错了部位** |

### 3.3 关键翻转：原清单"借页面分类"是借错了部位 ⚠️

当初把 TSP 的**页面分类**（看板/自选/策略/回测/数据）当成借鉴对象，切成 7 页。新地基下这是**错的借用方式**：

- TSP 的页面是"**监控视角**"——它的用户是盯着一屏看全市场的研究员；
- 我们的界面应是"**闭环视角**"——用户每天走 ①→⑥，界面以"今日闭环"为脊，操作（同步/扫描）常驻顶栏，而不是平铺一堆查看页。
- 所以：**TSP 的"页面皮"少借、甚至不借；TSP 的"操作型 UX 与后端结构"多借**。这才是它真正值得参考的价值。

> 一句话：TSP 值得借的是"**怎么做一个能跑任务、能流式报进度、好看的网页工作台**"，不是"**它有哪些页面**"。

## 4. 新原型的信息架构（以"闭环"为脊，不以"查看页"为脊）

不再把"看板/信号/自选/策略"平铺成查看器，而是围绕你的 6 步：

- **顶栏常驻动作**：「同步数据」「扫描策略」两个按钮（带进度条/终止），这是每日循环的入口，必须常驻、必须真能点（这正是从 TSP 的"操作型 UX"借来的）。
- **信号中心** = 第②步初筛结果，列表含 PA 证据列、失效价、不显示字母评级，行点击 → **TV 宿主抽屉**（第③步）。
- **计划页** = 第④步，接 `weekly_ambush_plan.md` + 每信号计划记录。
- **复盘/回测页** = 第⑥步，接 `journal` 表（回测可视化借 TSP 模式）。
- **策略页 / 自选页**：作为"查看/组织"辅助，数据全动态读注册表，不硬编码（自选双视图借 TSP）。

**首页建议做成"今日闭环"视图**：顶部同步/扫描状态 + 今日新信号流 + 待处理计划/持仓提醒，一眼看全今天要干的事。

## 5. 与《需求规格与设计方案》的冲突清单（需同步修订）
