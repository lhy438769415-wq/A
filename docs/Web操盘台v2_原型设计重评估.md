# Web 操盘台 v2 — 原型设计「重新评估」（纠偏书）

> 依据 2026-09-08 全天对话重新锚定方向。本文**不修改**现有原型 HTML，而是把走偏的地基推倒重设，作为后续重建的准绳。

## 0. 一句话结论

之前把原型当成"**4→7 页的只读查看器**"来做，这是错的地基。正确的地基是：一个以**淘汰 Tk、跑通交易员 6 步闭环**为目标的**通用可插拔 PA 策略框架界面**。今天几轮对话已经把错路暴露清楚，接下来应**按新地基重建原型**，而不是在旧 HTML 上补丁式修改。

## 1. 今天踩偏的 4 个坑（为什么之前是错路）

1. **场景评审写成了"系统页面点击流"**（A 档 = 打开看板→点事件流），不是交易员真实操作。被你一眼识破："交易员每天的高频操作是这样的吗？"
2. **把"缺口"当成了普适高频项**（缺口存活列、按周存活检查当成所有交易员标配）。违背你强调的："本工具是灵活添加策略的通用框架，不是每个时期都关注缺口"。
3. **原型定位成"只读看+筛"**，导致同步/扫描不在 Web 里，我甚至让你"继续用 Tk 点下载行情"——直接撞第 8 条决策"Tk 最终退役、Web 是唯一长期界面"。
4. **一轮轮补丁式迭代**（UX 评审→改、场景评审→改、TV→改），每次只动局部，从没回头重校地基，越改越偏。

## 2. 重新锚定的正确地基（今天已确认的事实）

- **工具定位**：通用、可插拔策略的 PA（价格行为）量化扫描框架。GUI 不得写死任何单一策略逻辑（尤其不能"缺口中心化"）；策略与信号一律从注册表动态读取 `get_metadata()['display_name']`，禁止硬编码中文花名。
- **交易员 6 步闭环**（你亲定的）：①同步数据 → ②扫描策略(初筛) → ③TV 里打开高质量形态(人工精筛) → ④制定交易计划 → ⑤持仓管理 → ⑥复盘分析(含回测)。
- **GUI 职责边界**（哪些归工具、哪些归人）：
  - ①同步、②扫描：**工具做**，且**必须进 Web**（这是淘汰 Tk 的前提）。
  - ③TV 精筛：**桥接/宿主**——Web 内嵌真 TV 控件 + 旁置 PA 证据（失效价/证据列/EV），不复制图表工作站。已验证可行，已做进信号抽屉。
  - ④计划：部分工具（`weekly_ambush_plan.md` 雏形 + 每信号计划记录）、部分人工。
  - ⑤持仓：基本人工（在券商/同花顺），GUI 只做跟踪/提醒，**不下单**。
  - ⑥复盘(含回测)：工具做（`journal` 表已存在 + 回测页）。
- **字段/命名铁律**：所有策略名、信号字段必须对齐真实注册表与 `signal_archive` 表结构，不出现无数据源字段。
- **红线 D5 修订**：Web 详情 K 线从"lightweight-charts 库"改为"内嵌 TV 控件"（待你拍板，但原型已按此落地）。

## 3. 新原型的信息架构（以"闭环"为脊，不以"查看页"为脊）

不再把"看板/信号/自选/策略"平铺成查看器，而是围绕你的 6 步：

- **顶栏常驻动作**：「同步数据」「扫描策略」两个按钮（带进度条/终止），这是每日循环的入口，必须常驻、必须真能点。
- **信号中心** = 第②步初筛结果，列表含 PA 证据列、失效价、不显示字母评级，行点击 → **TV 宿主抽屉**（第③步）。
- **计划页** = 第④步，接 `weekly_ambush_plan.md` + 每信号计划记录。
- **复盘/回测页** = 第⑥步，接 `journal` 表。
- **策略页 / 自选页**：作为"查看/组织"辅助，数据全动态读注册表，不硬编码。

**首页建议做成"今日闭环"视图**：顶部同步/扫描状态 + 今日新信号流 + 待处理计划/持仓提醒，一眼看全今天要干的事。

## 4. 与《需求规格与设计方案》的冲突清单（需同步修订）

| 操作搬家(同步/扫描)放二期 | 同步+扫描前置到阶段 1 收尾，让 Web 尽早拥有每日循环 |
