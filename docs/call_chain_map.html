② 主循环：猎人扫描循环（找新机会）

🟢 猎人循环 — 顺着箭头看一遍就懂

阶段一
数据同步
把最新行情拉进本机数据库（日线 / 周线各一招）。只读网络、本地存。
➜
阶段二
策略扫描
全市场挨只翻 K 线，按形态规则（缺口 / _pinbar 等）初筛候选。
➜
阶段三
AI 二次审计
（可选）DeepSeek 把关，过滤假信号。多数策略暂关。
➜
阶段四
信号归档
把命中的提醒写进 signal_archive 表，先标「待命」。
➜
阶段五
推送提醒
通过 Discord 发你文字指令 + K 线图，提醒你去看。

这条循环只负责「找新机会并提醒你」。它扫完就收工——不会回头管老信号是死是活。这就是问题的源头。

③ 守护循环：状态 / 持仓守护（管老信号死活）

🔴 守护循环 — 它才是「状态检测」的担当

状态机
信号状态机
翻出所有「待命/持仓中」信号，拿最新价核对：摸到入场→持仓；缺口补掉→失效；到止盈→盈利；到止损→止损；拖太久→过期。
➜
持仓管家
持仓管家(老血脉)
读你手填的 hold_list.txt，带成本线，让 AI 帮你判断「该不该拿」。
➜
输出
守护报告
把更新后的状态 / 持仓结论，发 Discord 或写报告。

关键事实：状态机本身写得对、算得准。问题只在「谁去按它的开关」——见下方缺陷卡。

🔴 接线缺陷：为什么「死票」还显示活着？

状态机（守护循环）从设计上没被「焊」进扫描循环。结果：

  • 你用 VS Code 跑周线扫描（命令行）→ 扫完只归档新信号，没人跑状态机 → 老信号状态永远冻在最后一次手动跟进时 断线
  • 你用 GUI 周线按钮 → 凑巧按钮里多写了一步跟进，状态会更新；但 日线按钮和命令行都没这步 → 你换入口就结果不一样 不一致
  • 日线扫描 → 任何入口都不跟进，日线信号状态机等于长期没自动跑过 断线

一句话：系统不是算错了，是「扫描」和「更新状态」被拆成了两件事，状态更新没接进扫描流程。所以你看到「缺口早补掉了，状态栏还写持仓中」——那是旧快照，没实时重算。

根治方向（你拍板后才动）：把状态机那一步直接塞进底层扫描函数，让 GUI / 命令行 / 日线 / 周线扫完都自动跟进，行为彻底一致。

④ 信号的一生（状态机到底管什么）

这是守护循环里「状态机」一格里那套规则的可视化。看懂它，你就知道为什么它需要「每次扫描都跑」。

待命 PENDING
刚被扫出，标好入场价/止损价，等着价格来碰
➜
持仓 ACTIVE
价格摸到入场价 → 变成「持仓中」
➜
盈利 WIN
碰到止盈价 → 赚到了
↘
止损 LOSS
碰到止损价 → 认栽
↙
失效 INVALIDATED
缺口被回补 → 形态破功
↙
过期 EXPIRED
拖太久没动静 → 作废

这 6 个状态都在 core/signal_tracker/tracking.py 里。每次状态机跑一遍，就是把所有「待命/持仓」的信号，对照最新行情往右推一格。它不跑，信号就卡在左边不动。

⑤ 地基：数据从哪来

行情数据库
data/ 下的 SQLite 文件（日线 / 周线 / 信号归档各表）。系统是离线 T+1，数据先同步进这里才扫描。
数据层 data_provider
负责拉行情、本地聚合周线。同步的入口，所有扫描都吃它的数据。
数据库层 database
所有表结构的唯一主人（schema 不能散落别处）。
