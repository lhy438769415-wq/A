> 用途：提交第三方（运行环境 / 平台侧 / 技术评审）评估"每日首次运行必现异常提示、二次运行正常"的根因
> 阅读对象：具备 Python / Windows 终端知识的工程师

## 0. 给第三方的阅读指引（30 秒版）

- **已知**：程序在**每天第一次运行**时必现一段 `KeyboardInterrupt` 报错提示；**同一天第二次运行完全正常**。
- **已加诊断工具**：一个"死亡记录仪"（把收到中断信号的精确位置写进日志）。它**在运行阶段工作正常**（有 5 次成功记录），但**在 import（导入依赖）阶段是盲区**（用户每天遇到的那次恰恰没被记录）。
- **当前倾向判断**：冷启动慢 → 用户误以为卡死 → 手动 Ctrl+C。但**缺少决定性证据**（盲区没记录到信号来源）。
- **需第三方确认**：运行环境（尤其 WorkBuddy 沙箱 / 终端）在子进程启动初期，是否会发送中断信号或超时中断。

## 1. 问题现象

- **触发**：每天第一次运行 `hunter.py`（A股日线价格行为扫描，收盘后由交易员在 VSCode 终端人工触发）。
- **表现**：终端打印一大段报错，核心是 `KeyboardInterrupt`（Python 的"收到 Ctrl+C / 中断信号"异常），堆栈指向 `import sqlite3` → `Lib/sqlite3/dbapi2.py:51`。
- **不出现**：同一天内第二次及以后运行，无任何提示，程序正常结束。
- **用户痛点**：用户是交易者而非程序员，无法判断"这是真报错还是环境问题"，也不敢确认程序是否跑完了。

## 3. 复现规律（多次观察一致）

1. 必现于"当天首次运行"（冷启动：OS 文件缓存为空、杀软对 `.venv` 做首次扫描）。
2. 首次运行在 import 阶段会出现**数秒无输出的空白期**，随后报错。
3. 同日后续运行无此空白期，也不报错。
4. 与 2026-08-12 的历史事件高度相似：当时 pandas 冷启动加载约 10 秒空白 → 用户误以为卡死 → 手动 Ctrl+C → 同样的 `KeyboardInterrupt`。

## 4. 已做的排查与客观证据

### 4.1 死亡记录仪（诊断工具）机制

- 定义：`hunter.py:56-93`，含 `_sigint_death_recorder()`（信号处理函数）与 `_install_death_recorder()`（注册函数）。
- 安装位置：`hunter.py:1392`，位于 `if __name__ == "__main__":` 块内，**在所有 import 语句执行完毕之后**才调用。
- 作用：一旦收到 `SIGINT` / `SIGTERM`（外部中断信号），立即把"时间戳 + 当前卡在哪个文件哪一行哪个函数"追加写入 `data/crash_log.txt`，再走 Python 默认流程。

### 4.2 crash_log.txt 实证（最关键证据）

日志中共有 5 次成功记录，规律如下：

| 日期时间 | 记录到的停止位置 | 是否在运行阶段 | 是否成功记录 |
|---|---|---|---|
| 2026-08-13 19:37 | `check_database_health()` (line 858) | 是（import 早已完成） | ✅ 已记录 |
| 2026-08-14 22:50 | `main()` (line 1129) | 是 | ✅ 已记录 |
| 2026-08-14 22:50 | `main()` (line 1250) | 是 | ✅ 已记录 |
| 2026-08-17 19:50 | `check_database_health()` (line 957) | 是 | ✅ 已记录 |
| 2026-08-17 19:53 | `check_database_health()` (line 957) | 是 | ✅ 已记录 |

**关键反证**：用户每日"首跑报错"的那一次（例如 2026-08-15 截图所示 import 阶段的 `KeyboardInterrupt`），在 `crash_log.txt` 中**没有任何对应记录**。

### 4.3 由证据推出的结论

- 死亡记录仪**本身是好的**：运行阶段的信号 100% 被捕获（上表 5/5）。
- **唯一盲区在 import 阶段**：记录仪在 import 全部完成后才安装，因此 import 期间发生的任何中断信号都"看不见、记不下"。
- 用户每天遇到的首跑报错，恰好落在这一盲区——这正是我们无法定论的根本原因。

## 5. 两种可能根因（需第三方协助定论）

### 可能性 A：冷启动慢 → 用户误按 Ctrl+C（主观概率较高）

- 冷启动时空白期数秒，用户误判为卡死而手动 Ctrl+C。
- 佐证 1：与 2026-08-12 事件机理完全相同。
- 佐证 2："首跑出现 / 次跑消失"完美匹配"冷启动 vs 热缓存"特征。

### 可能性 B：外部信号源在启动初期中断了进程（未排除）

- 某些环境组件在子进程刚启动、尚未进入业务逻辑时就发送了中断：杀软、VSCode 终端、WorkBuddy 沙箱、PowerShell 超时器等。
- **当前无法证伪**：因为盲区（import 阶段）没记录到"谁发的信号"。

## 7. 拟定的代码侧修复（立即可做，与根因无关）

- **目标**：把死亡记录仪的安装时机从 `hunter.py:1392`（import 之后）提前到**所有重型 import 之前**，让它在 import 一开始就已上岗。
- **技术注意点**：`signal.signal()` 只能在主线程调用；原作者在 1392 处安装正是为了避免干扰测试脚本（测试 import 本模块时可能不在主线程）。因此提前安装需保护，可行方案是：**将重型 import 收进一个 `def _load()` 函数，在 `if __name__ == "__main__":` 块的最开头先安装记录仪，再调用 `_load()`**。这样 import 阶段也被覆盖，且不触碰测试路径。
- **修复后预期**：若再发生首跑 `KeyboardInterrupt`，`crash_log.txt` 会精确记录"当时停在 `import sqlite3` / `dbapi2.py:51`"，凭此一行即可定论是人为还是环境信号。

## 附：术语小注（供非 Python 背景阅读）

- **KeyboardInterrupt**：Python 收到"中断"时抛出的异常，最常见来源是用户按 `Ctrl+C`，但外部进程 / 系统也能发送等价信号。
- **SIGINT / SIGTERM**：操作系统向进程发的中断 / 终止信号；`Ctrl+C` 对应的就是 SIGINT。
- **冷启动 / 热缓存**：程序 / 文件第一次运行时系统要从磁盘读取并可能被杀软扫描（慢）；再次运行相关内容已在内存缓存中（快）。
- **import 阶段**：Python 运行脚本时，先要把所有依赖库加载进内存，这一步发生在任何业务代码之前。
