# 工程成熟度提升方案（Engineering Maturity Plan）

> 背景：本项目（Brooks-AI Quant System V10.0）功能可用，但多次出现"AI/协作者未完整理解代码就给出建议/改动"的问题。
> 本文不讨论具体功能修复，只讨论**如何让项目变得"可被可靠理解、可被安全改动"**——这是工程与"脚本式编程"的根本差距。
> 参考：*Software Engineering at Google*（编程 vs 软件工程）、ADR（Michael Nygard）、Living Documentation（Cyrille Martraire）、Building Evolutionary Architectures（适应度函数）、DORA/Accelerate（工程效能度量）、Google Engineering Practices（代码评审）。

---

## 0. 一句话诊断

本项目现在是**"为作者本人能跑通而写的程序"**，还不是**"为团队/未来/AI 能安全维护而写的软件工程"**。
差别在于：**可理解性、可变更性、规范可执行性，都是靠结构保证的，不是靠个人记忆或纸质文档保证的。**

本次"AI 没读全就建议"只是表象，根因是项目缺乏让"不理解"无处藏身的工程结构。

---

## 1. 根因清单（用工程视角重新归因）

| # | 现象（已核实） | 根因（工程视角） | 为什么会导致"猜了就改" |
|---|---|---|---|
| R1 | 规范/版本漂移：STATUS 写 V9.8、实际 V9.20；测试基线 25/25 vs 98/98；`LOGIC_AUDIT_RULES.md` 被引用却不存在 | **文档与代码双向漂移**，无单一事实源（SSOT） | 任何人都只能凭记忆/旧快照判断，AI 尤甚 |
| R2 | 红线指定用 `core/paths.py`/`core/log_config.py`，但两文件都不存在 → 全项目仍有 61 处 `sys.path.insert`、49 处 `basicConfig` | **规范不可执行**（纸面约束，无工具兜底） | "禁止 X"成空话，违反零成本，越积越多 |
| R3 | 无 CI、无评审门禁、无预提交钩子 | **变更无护栏** | AI/人都能"猜一下就改、改完就推"，无强制验证 |
| R4 | 双扫描引擎、1408 行 `signal_tracker` God Function、周线 `if 'PINBAR' in name` 后缀 hack | **模块边界缺失** | 局部改动会悄悄破坏全局，且无机制报警 |
| R5 | 8 个文件全项目 0 引用；还有 `feature_pipeline`/`personas`/`monitor` 等 0 引用"备件" | **死代码无自动检测** | 维护者误以为还在用，认知熵持续累积 |
| R6 | 关键知识只存在于设计者脑中 + 散落 `.agent/.agents` 规则 | **Bus Factor = 1 / 部落知识** | 离开设计者本人，系统不可重建、不可交接 |

> 结论：R1–R6 全部指向同一个事实——**项目没有"让真相自动浮现"的机制**。修一处文件、删几个死代码，都只是治标；治本是建立下面五大支柱。

---

## 2. 体系化解决方案：五大支柱

> 设计原则：**不靠人自觉，靠结构强制**。每一项都对应一个行业最佳实践，并直接消除 R1–R6 中的某一类根因。

### 支柱 A — 单一事实源 + 活文档（SSOT & Living Documentation）
**治 R1、R6。**

- **架构决策记录（ADR，Michael Nygard）**：每个重要决定（为何离线优先、为何双引擎、为何 T+1）写成 `docs/adr/NNNN-*.md`，含"背景/决策/后果"。替代口头/记忆，决策者可回溯。
- **模块地图由代码生成，不手画**：用 `pydeps`/`graghiz` 或自定义脚本从 import 关系自动产出调用图（C4 模型思想）。本次我手维护的"调研清单"会漂移，正确做法是**跑出来的**，不是写出来的。
- **活文档（Living Documentation）**：公共 API 的 docstring 即文档源；用 `mkdocs`/`pdoc` 从代码抽取，随版本构建。文档与代码同仓、同 PR、同评审 → 漂移在合并前就被挡住。
- **版本号与状态单点**：README/STATUS 的版本由 CI 在发版时自动写入，禁止手改。

### 支柱 B — 变更护栏（Change Guardrails）
**治 R2、R3。直接杜绝"猜了就改"。**

- **CI 门禁（每次改动必过）**：`ruff`(lint) + `mypy`(类型) + `pytest`(测试) 三道关，未过不准合并。AI 的每次产出也必须过 CI 才算"完成"。
- **预提交钩子（pre-commit）把红线变代码**：
  - 用 `ruff` 自定义规则或 `flake8-todo`/`regex` 钩子，**直接报错** `sys.path.insert`、`logging.basicConfig`，而不是写在 AGENTS.md 里让人"记得别用"。
  - 必须先**补建** `core/paths.py` 与 `core/log_config.py` 这两个红线指定的合规出口（消除 R2 的前提）。
- **代码评审门禁（CODEOWNERS）**：保护分支 + 即使 AI 改动也需人工 approve。**这正是对本次"跳过理解就建议"的直接机制约束**——任何改动要合并，必须有第二双眼睛（人或另一 Agent）基于 CI + 文档确认。
- **Trunk-based + Protected Branch**（Google Engineering Practices）：小步提交、保护主分支。

### 支柱 C — 测试即规格（Tests as Executable Spec）
**治 R3、R4、R5。**

- **"我解释不清的行为 = 缺测试"**：把测试当作系统行为的权威说明。凡 AI/人无法解释的代码路径，先补 characterization test（GBST，对遗留代码兜底的"特征测试"），再谈改动。
- **契约测试锁定公共接口**：策略自描述接口（`get_metadata` 契约）、信号生命周期状态机，用契约测试冻结，未来任何破坏都会被 CI 抓出。
- **dead-code 自动扫描**：CI 接入 `vulture`，0 引用文件/函数自动标红，死代码不再靠人工 grep。

### 支柱 D — 边界与模块化（Bounded Contexts + Fitness Functions）
**治 R4。**

- **明确包级公共 API**：`core/`（引擎）、`tools/`（工具）、`strategies/`（插件）、`patterns/`（形态）各自只暴露约定接口，内部实现可换。
- **架构适应度函数（Building Evolutionary Architectures）**：把"指标/信号/推送三阶段不得循环依赖""周线与日线必须共用同一份元数据"写成**可在 CI 跑的断言**（如 import 环检测、依赖方向检查）。双引擎之类漂移，在合并前就被适应度函数报警。
- **God Function 拆分**有测试兜底后渐进进行，不一次性大重构（降低风险）。

### 支柱 E — 可观测与效能度量（DORA）
**治 R1、R6 的持续性。**

- **技术债仪表盘**：CI 定期产出"死代码数 / 红线违反数 / 测试覆盖率 / 循环依赖数"，趋势可见。
- **DORA 四指标**（Accelerate）：部署频率、变更前置时间、变更失败率、恢复时长——哪怕本项目是单机定时任务，也可用"扫描任务成功率/推送到达率/人工介入次数"代理。
- **知识交接检查**：关键模块必须有 ADR + 活文档 + owner，否则 CI 告警（防 Bus Factor=1）。

## 3. 落地路线（渐进裹挟，不推倒重来）

> 原则：**用工程纪律把现有项目"裹"起来**，每步都可独立验证、可回退，不阻塞现有功能。

| 阶段 | 目标 | 具体动作 | 消除的根因 | 产出 |
|---|---|---|---|---|
| **P0** | 红线可执行 | 补建 `core/paths.py`、`core/log_config.py`；加 `pre-commit` 钩子报错 `sys.path.insert`/`basicConfig` | R2 | 规范从纸面变代码 |
| **P1** | 最小 CI | GitHub Actions / 本地 runner：ruff + pytest（先跑通现有 25/25 基线） | R3 | 改动强制验证 |
| **P2** | 真相可溯 | 建 `docs/adr/` 写前 5 个关键决策；CI 自动生成模块调用图 | R1、R6 | 决策与结构可回溯 |
| **P3** | 接口冻结 | 为策略自描述接口、信号状态机补契约测试；接 `vulture` 死代码扫描 | R4、R5 | 行为有规格兜底 |
| **P4** | 边界锁定 | 写架构适应度函数（依赖方向/共用元数据断言） | R4 | 漂移合并前报警 |
| **P5** | 持续度量 | 技术债仪表盘 + DORA 代理指标周报 | R1、R6 | 健康度可见 |

---

## 4. 这套体系如何根治"AI 没读全就乱建议"

逐条对应：

1. **活文档 + 自动模块图（A）**：项目自身"说清楚自己"，AI 不必人肉通读几千行——真相由工具浮现。
2. **CI 门禁（B）**：任何改动（含 AI 的）必须过 lint/type/test，猜错立刻失败，没有"蒙混过关"空间。
3. **评审门禁（B）**：AI 产出要合并需人工 approve，等于强制"第二双眼睛复核理解"，正是本次缺失的环节。
4. **契约测试（C）**：行为被测试冻结，AI 改动若误解语义会红，逼它先理解再动。
5. **适应度函数（D）**：模块边界被断言锁住，局部瞎改会报警，杜绝"双引擎式"隐性漂移。
6. **ADR（A）**：决策 rationale 在仓内，AI 不必猜"当初为啥这么设计"。

> 一句话：**让"不理解"在合并前就被结构和工具拦下来，而不是靠 AI 的自觉。**

---

## 5. 与既有规范的衔接（不另起炉灶）

- 本方案**不推翻** `.agent/rules/*` 与 `optimization_fix_plan.md` 的共识，而是把它们**从"文档"升级为"可执行机制"**（P0 的 pre-commit 即把红线变代码）。
- 既有 20 条债务清单纳入 P3–P5 的技术债仪表盘跟踪，优先级按 `optimization_fix_plan.md` 的 Tier 不变。

1. 批准本框架（或提出调整）。
2. 若批准，我建议**先落地 P0（最小、零功能风险、立刻消除 R2）**：补建 `core/paths.py` + `core/log_config.py` + `pre-commit` 配置，把红线变可执行。
