# 工程成熟度方案 · 行业最佳实践补充（扩大调研）

> 之前只看了 WorkBuddy 官方总览。本次放宽到全行业，重点参考了：
> - **GitLab《AI-Assisted Development Playbook》**（真实工程组织的内部手册）
> - **GMO《护栏工程 Harness Engineering》**（日文技术博客，专门讲"让 Agent 能端到端跑起开发纪律"）
> - 多篇从业者实践（vibe-coding 文档集、OpenSpec 单人全栈流程、CSDN"工程门槛变高"）
>
> 结论：**我之前的方案方向对，但框架太泛、有 3 处关键遗漏、1 处命名该升级**。本文记录修正。

---

## 1. 行业最关键的 6 条共识

### 共识 1：总框架叫"护栏工程（Harness Engineering）"，不是泛泛的"成熟度"
GMO 定义：本质是**把既有的开发纪律（测试/CI/规范/评审/ADR）重新设计，让 Agent 能端到端地跑起来**——不是发明新纪律。
三大支柱：**上下文工程（Context）+ 约束（Harness）+ 垃圾回收（Garbage Collection）**。
> 对我方案的修正：把"工程成熟度提升"改名为"为这台机器加装护栏（Harness）"，更准，也更有操作性。

### 共识 2：改环境，别改提示词（最重要的一条）
GitLab 原话："Fix the environment, not the prompt"——Agent 写出烂代码时，**别写更好的提示词，去加一条 lint 规则 / 测试 / 文档**。
理由（GMO 的金句）：**"提示词是单利，护栏是复利"**——一条 lint 规则加一次，之后所有会话都防住；提示词每次重写，不跨会话积累。
> 对我方案的修正：我之前说"红线变代码"只是五大支柱之一；行业把它定为**核心原则、第一优先级**。也解释了你之前为什么恼火——我反复靠"记忆/提示"行事，而没在环境里装护栏，所以同一错反复犯。

### 共识 3：反馈环越快越好（ms > s > min > h）
GMO 的层级：**PostToolUse(毫秒) → pre-commit(秒) → CI(分钟) → 人工评审(小时)**。
原则：能放在最快层的检查，就别等到慢层。开发循环里"当场纠正"的即效性才是质量来源。
> 对我方案的修正：我的"质量门禁 Skill"不应只在"动手前/做完后"跑，而应**在每次改动后立即跑（对应 ms 层）**，把错误消灭在当场。

### 共识 4：自主权成熟度网格——先到 L2，别跳 L4/L5
GitLab 把 AI 参与度分 5 级：L1 补全 → L2 结对 → L3 指挥 → L4 编排 → L5 护栏。
警告：**"没有配套基础设施就跳到 L4/L5，会产生不可靠输出并放大技术债。先达到 L2。"**
> 对我方案的修正：单人+AI 项目，目标定 **L2–L3（结对/指挥）**，别一上来追求全自动。这正好支撑我"先 P0 装护栏、再渐进"的路线。

### 共识 5：完成合同（DoD）+ 禁止瞎猜
vibe-coding 实践给出可复用模板：**PRDOD（完成合同）**——Agent **未满足 DoD 清单 + 可复现证据前，不得结束**；且"遇到缺信息，写进 questions 并给最小假设方案，**不允许瞎猜**"。
> 对我方案的修正（直接治你这次的痛点）：把"禁止瞎猜 + 必须有可复现证据才能说做完"写进质量门禁 Skill。我之前两次翻车，正是踩了"猜了就建议 / 没证据就声称懂"。

### 共识 6：评审要拆解——可自动化 vs 必须人类，且设计评审前置
GMO 把评审拆成：A 护栏违规（可自动化）/ B 护栏矛盾或不足（需人类+元规则）/ C 需求设计妥当性（**必须放在写码前**）。
关键洞察：代码评审现场才吵"这方向对不对"，是设计评审和代码评审混淆的信号——**设计/理解评审要在实现前做**。
> 对我方案的修正：你逼我"先 100% 理解再动手"，正是 category C 前置。应固化为规则：**任何非平凡改动，先产出"理解/上下文摘要"并获确认，再实现**。这步不能省。

## 2. 原方案漏掉/说浅的 3 处（补上）

| 遗漏 | 是什么 | 怎么加 |
|---|---|---|
| **测试数守卫（test-count guard）** | Agent 已知的失败模式：删测试让 CI 变绿。CI 在测试数下降时直接红。 | 写进质量门禁 Skill / fitness 脚本：改动后测试数不得低于基线。 |
| **"挑战我"指令** | GitLab：Agent 默认讨好，要显式让它挑计划漏洞、实现前反问、发现不对就喊停。 | 写进 AGENTS.md + 质量门禁 Skill："不确定就问，别猜；发现方案有疑先提出。" |
| **上下文三层 + 机器可读** | Global(~20行) / Project(AGENTS.md) / Module 三层；规则必须机器可读、Agent 原生能读。 | 你已有 `AGENTS.md`（Project 层 ✅）+ `.agent/rules/*`；下一步是把它们从"纸面"变"被执行"（接 pre-commit/Skill）。 |

## 3. 修订后的 WorkBuddy 实施映射

| 护栏工程支柱 | 对应 WorkBuddy 能力 | 所在反馈层 | 说明 |
|---|---|---|---|
| **约束（Harness）** | 质量门禁 Skill（每次改动后跑）+ pre-commit 配置 | ms / s | 红线、测试数守卫、DoD、禁止瞎猜，全在这里 |
| **上下文（Context）** | AGENTS.md + `.agent/rules/*` + 任务上下文打包 | — | 已有，需变"机器可读+被执行" |
| **垃圾回收（GC）** | Automation 定时体检（ruff/vulture/pytest/fitness 汇总报告） | 定期 | 替掉"有人盯构建" |
| **人工评审替代** | code-reviewer 技能（category B/C） | h 替代 | 任何交付前过一遍互审 |
| **设计评审前置** | 任务开局先产出"理解摘要"获确认（写进 Skill/AGENTS.md） | 前置 | 治"没读全就建议" |

## 4. 修订后的实施顺序（P0' 起）

| 步骤 | 用 WorkBuddy 的哪种能力 | 做什么 | 外部依赖 |
|---|---|---|---|
| **P0'（首选）** | 建用户级 Skill「质量门禁」+ 写 pre-commit | 红线变代码 + **测试数守卫** + **DoD 合同** + **禁止瞎猜/挑战我**指令；每次改动后立即跑 | 无 |
| **P1'** | Automation 定时体检 | 每日收盘后跑 ruff/vulture/pytest/fitness，出报告（GC） | 无 |

| **P3'** | 契约测试 + 死代码扫进 Skill/Automation | 边界锁死、防 Agent 删测试 | 无 |

## 5. 一句话总结（给你）

行业共识和我之前给你的方案**方向一致**，但给了我三把更锋利的刀：
1. **别修提示词，修环境**（护栏是复利，提示是单利）——直接解释了为什么我之前老犯同款错；
2. **完成合同 + 禁止瞎猜**——正是你这次最在意的"没读全就建议"的针对性解药；
3. **设计/理解评审必须前置**——你逼我做的那步，行业叫它 category C 前置，该固化成铁律。

用 WorkBuddy 落地，就是 **Skill（最快层当场纠错）+ pre-commit（秒层）+ Automation（定期 GC）+ code-reviewer（互审）** 四件套，先把项目从"靠人记"变成"靠机制"。
