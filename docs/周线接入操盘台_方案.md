## 三、六个新发现（v1 未覆盖，全部实测/读码）

### 发现 1：库里 86% 的周线信号是回测回填，不是实盘信号 🔴

- 3148 条周线信号中，**2622 条入库于 2026-05**（一次性），**526 条**来自每周实盘扫描。
- 这 2622 条的 signal_date 横跨 **2011-04-01 ~ 2026-05-29**，其中 **2611 条状态是 WIN**。
- 判定依据：signal_date 跨度 15 年、状态几乎全 WIN、scan_date 被写成 2014/2015 年的历史日期（模拟历史扫描）。

**影响**：方案 v1 第 3 步"所有查询加 `AND timeframe='weekly'`"做完后，
你切到周线，日期下拉框里会出现 2011 年起的几百个日期，清单里躺着一堆早已平仓的历史信号。
**必须先做数据治理**，否则这个页面没法用。

### 发现 2：周线扫描是"回看 60 周"，不是"只看本周" 🔴

- `scan_engine.py:161` `scan_single_code_weekly(code, signal_lookback=60, ...)`，
  函数注释明确写："缺口家族需回看较宽窗口(默认60周)以捕捉仍存活的 pending/active 信号"。
- `scan_weekly_gap_signals` 的 `recent_weeks=4` 参数**根本没传给单票函数**（`:363` 只传了 code 和 strategies），
  所以界面上写"检查最近 4 周"是**假的**，实际回看 60 周。
- 证据：2026-08-01 那次扫描，归档了 signal_date 为 `2025-11-28`、`2025-09-19`、`2025-08-15` 的信号（几个月前的）。

**影响**：
- 这不是 bug，是缺口策略的设计意图（"信号还活着"就有意义，跟日线"只推当天触发"的口径不同）。
- 但**归档是幂等的**（`signal_id = code_strategy_timeframe_signal_date` + `INSERT OR IGNORE`，`archive.py:32/48`），
  所以**不会重复入库**；而 **Discord 推送是全量推**（`scan_engine.py:595` 起 `for s in sig_gap`），
  **每周会把近 60 周的老信号重新推一遍**。

> 这是"每周跑一次周线"最实际的副作用：**Discord 会收到一堆几个月前的旧信号**。
> 是否要处理，取决于你——见第六节待拍板问题 B。

### 发现 3：每次全市场扫描扫出约 29 条，不是"一周两三只" ⚠️ 口径已修正

**v2 初稿在这里写错了，现按实测更正。** 初稿拿"归档进库的条数"当成了"扫描产出"，
但归档有两个特性会严重压低这个数字：
① 只归档**已确认**信号，待确认（未破位）的 16 条不进库；
② 归档是幂等的（同一条信号重复扫只记一次），上周归过的这周不重复入库。

**实测（2026-08-30，全市场 3312 只，本机实跑 6.7 分钟）：**

| 口径 | 数量 | 说明 |
|---|---|---|
| **扫描扫出总数** | **29 条** | 这是界面/推送里能看到的数量级 |
| — 结构性缺口 GAP H1 | 24 条 | |
| — GAP H2 | 3 条 | |
| — GAP PINBAR | 1 条 | |
| — 3K | 1 条 | 3K 路径不归档进库 |
| 其中 待确认（未破位） | 16 条 | 👀 只进监控名单，不推送归档与否见下 |
| 其中 已确认 | 12 条 | ✨ 会推送 + 会归档 |

> 大白话：每周跑一次周线，你会看到**三十来只**票，其中约一半已经破位确认、另一半还在等触发。
> 周线页面**不会空**。

**由此引出两个必须说清的差异**：

**① 界面看不到那 16 条"待确认"**。界面读的是库，库里只有已确认信号（这是你 7-30 定的
"只归档通过信号"），所以待确认的票只在推送和监控名单文件里，操盘台里没有。
要让它进界面是另一个改动，需你另外拍板（本次不改）。

**② 更关键：29 条是散落在 60 周里的，不是集中在某一周。** 🔴

单次扫描扫出的 29 条，分布在 60 周回看窗口的**不同周**上。库里累计 526 条真实信号，
分布在 **59 个信号日**上，平均每个信号日只有几条：

| 信号日 | 条数 |
|---|---|
| 2026-08-21 | 1 |
| 2026-08-14 | 1 |
| 2026-08-07 | 2 |
| 2026-07-24 | 1 |
| 2026-07-17 | 1 |
| 2026-07-10 | 7 |
| 2026-07-03 | 7 |

> 也就是说：界面沿用日线那套"选某一天 → 看那天的信号"，切到周线后**选中最新周只能看到 1 条**。
> 这就是"看着少"的真正原因 —— 不是信号少，是**按单日切片的展示方式不适合周线**。
> → 需要给周线单独设计列表口径，见第六节新增的问题 C。

### 发现 4：数据质量有两处硬伤

| 问题 | 数量 | 现状 | 是否阻塞 |
|---|---|---|---|
| signal_date 是垃圾值（`99`/`97`/`90`/`762` 等） | 674 条 | 现有 `_DATE_LIKE = "____-__-__"` 已能过滤 | ❌ 已有解 |
| 一批信号把「结构性缺口 GAP H1」记成了**早期内部写法**，未被现行 key 收录 | 周线实盘里 **469 条** | 界面按现役 key 统计 → **整批漏掉** | ✅ 需在查询里归一 |

> 这不是"两个不同策略"，是**同一个策略（花名 GAP H1）的两种内部记法**。
> 处理方式：查询时归一到现役 key，不新增、不改动任何策略名。
> 日线同样存在历史遗留记法（`MTR_MASTER` 与早期写法并存、`UNKNOWN`、`TEST_STRAT`），
> 但按"不发散"原则，**本次只处理周线这批**，日线的另开一次。

### 发现 5：周线同步的成本结构

- `update_weekly_data_batch(max_workers)` **只接受一个参数**，不支持 `limit` / `all_codes`（`:1140`），
  → 只能全市场跑，无法"先试 100 只"。
- 当前状态：3312 只中 **3190 只已是最新**（2026-08-28），**122 只待更新**——
  这 122 只是长期停牌/退市股（000004、000005、000023…），每周都会被尝试更新。
- 同步主流程是**拿本地日线数据在内存里合并成周线**（`_fast_local_weekly_aggregation`，`:1060`），不走网络。

> 影响：同步本身很便宜；那 122 只停牌股每周空转一次，是小浪费，不阻塞。

### 发现 6：周线信号的"状态机"停摆了 4 个半月 🔴🔴（本次最严重，直接卡住你要的口径）

你选的口径是"**截至某一周、还在推送的所有存活信号**"。要回答"还活不活着"，
必须靠信号的状态（待确认 / 已入场 / 止盈 / 止损 / 失效 / 过期）。而周线这一块的状态**是坏的**。

**证据链（全部实测，未写库）：**

| 检查 | 结果 |
|---|---|
| 周线信号最后一次被更新状态 | **2026-04-11**（此后只新增、从不更新） |
| 库里"待确认"的周线信号 | 240 条，它们的"最后更新时刻" = 入库时刻，**从没被复查过** |
| 抽 20 条 6~7 月的"待确认"试算 | **20 条全部该变状态**（19 条早已入场、1 条已失效） |
| 全量 258 条未结周线信号试算（3.5 秒算完） | 195 条该转为**已入场**、43 条**失效**、11 条**止盈**、6 条**止损**、1 条**过期**、2 条不变 |

**为什么停了**：负责推进状态的那个动作（命令行里的"追踪"）自 4 月起就没再跑过。
日线之所以看起来正常，是因为日线每天都扫，新信号一进来就是新的；**但老信号的复查同样没人做**
（日线也有 694 条 7 月前的信号至今挂在"待确认"，本该早就过期了）。

**影响（这是关键）**：
如果现在就按库里的状态做"存活清单"，会给你列出 **258 条**，其中约 **230 条是幽灵**
——它们其实早就入场、止损、止盈或失效了，只是没人去更新。
你要的"点开看看有没有到止盈/止损"，在这个数据上也**答不出来**。

**好消息**：补一次不贵 —— 258 条全量试算只要 **3.5 秒**，不是几个小时。

## 四、需求本身的重新评估

### 结论：这个需求值得做，而且价值比 v1 估计的更高

项目自己的评级研究结论（15 年样本）：
**周线缺口家族期望收益为正**（H2 +0.381R / 结构性 +0.295R / Pinbar +0.482R），
**而日线普遍偏弱、部分为负**。

> 大白话：你这套系统里，周线才是真正有优势的那一块，日线是弱项。
> 但现在周线只能靠命令行跑、结果只在 Discord 看，桌面操盘台上**完全没有周线的位置**。
> 所以"补周线"不是补一个锦上添花的功能，而是**把你最有优势的武器搬上桌面**。

### 但有三个认知需要修正

**① "每周跑一次"是对的，但理由要换。**
v1 隐含假设是"周线很贵，所以少跑"。实测下来它并不贵（6~8 分钟）。
真正的理由是：**周线要等周五收盘才有新的一根 K 线**，周一~周四跑，数据是旧的，结果跟上周完全一样，等于白跑。
→ 所以正确的时机是**周五收盘后或周末**，一周一次就够，不是因为贵，是因为**没新数据**。

**② 默认停在"日线"仍然合理，但你可能低估了周线。**
默认日线是为了不打乱你现在的每天习惯（打开就能用）。保持不变。
但由于周线期望收益为正、日线弱，**周线页面可能才是你真正该多看的地方**。
→ v2 建议：状态栏在周线模式下，把"周线数据截至哪一周"显示出来，让你一眼知道该不该跑。

**③ 零自动化带来一个你需要知道的成本。**
程序不会提醒你（你定的红线 A）。所以"周六记得切到周线跑一次"完全靠你自己记。
→ 这是你自己选的代价。如果你哪天想加提醒，随时可以改，但现在按红线不做。

## 六、你的三个决定（已拍板，2026-08-30）

| # | 问题 | 你的决定 | 落地方式 |
|---|---|---|---|
| **A** | 周线清单显示多久 | **全部**（不要"近 N 周"的档位） | 下拉里不再放时间窗口，只放**周** |
| **B** | Discord 重复推旧信号 | **不改，继续全量推** | 推送侧零改动（你把它当第三方历史备份） |
| **C** | 周线清单怎么切 | **下拉以"周"为单位；选某一周 → 看"截至那一周、仍在推送的所有存活信号"** | ❗与原 C1 不同：不是"那一周新触发的"，而是"到那一周为止还活着的全部" |

### 决定 C 的准确含义（写死，避免再做错）

- 下拉里每一项 = **一个周**（跟日线"选某一天"对齐，只是粒度换成周）。
- 选中第 W 周后，清单 = 所有满足下面两条的信号：
  1. `信号日 ≤ W`（那一周之前就已经出现）；
  2. **截至 W 那一刻仍未了结**（要么至今未了结，要么了结日期晚于 W）。
- "未了结" = 状态是 待确认 / 已入场；"已了结" = 止盈 / 止损 / 失效 / 过期。
- 默认停在**最新一周**（跟日线默认停最新一天一致）。

> 大白话：这不是"这一周新冒出来几只"，而是**"到这一周为止，手上还攥着哪些票"**。

### ❗落地前必须先解决一件事：周线状态是坏的

决定 C 完全依赖"这条信号了结了没有"，而周线这一块的状态从 **2026-04-11 起就没更新过**（发现 6）。
现在直接做，会给你列 **258 条，其中约 230 条是幽灵**。

**必须先补跑一次周线状态推进（要写库，需你点头）**，三条路：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **甲（推荐）** | 补跑一次周线追踪（约 3.5 秒），之后**你每次手动跑周线扫描时，扫完顺带跑一次**（同一个手动动作内，不算自动化） | 状态永远是最新的；"到没到止盈/止损"能准确回答；历史周也能重建 | 要写一次库（约 258 条改状态，不删任何数据） |
